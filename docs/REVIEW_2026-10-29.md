# Code and deployed-site review — 29 October 2026

## Scope

Reviewed frontend pages, hooks and API/service boundaries; backend controllers,
validation, sessions, authorization, ride lifecycle, chat, email and deployment
configuration. Inspected public pages on the deployed Vercel site and read-only
health/auth responses from its published backend. The live bundle is an older
deployment: known contact-page and error-display differences were not treated as
new local defects. No production bookings, messages or database migrations were
created by this review.

## Changes

- Page-path changes reset scroll immediately, including navigation from footer
  links. Query-only searches retain their scroll position.
- Crash screens, sign-in URL messages, validation responses and ride-action
  failures use safe text instead of raw exception or parser messages.
- Request-list failures propagate to the page instead of looking like successful
  empty lists. Chat-list failures have an explicit retry option.
- Join requests expose a busy state and block duplicate submissions while pending.
- Search results cannot expose an old page's metadata as the completed result of
  a new search. Searching no longer rechecks authentication for every URL change.
- Profile row components have stable identities; the joining date comes from the
  actual account record instead of being guessed from an email address.
- HTTP and socket ride IDs share validation, reject coercion tricks and fit the
  PostgreSQL integer range. Missing request bodies return validation errors.
- Chat confirms persistence before clearing drafts, disables sending while
  disconnected, provides reconnection, preserves new messages when history
  arrives, limits the displayed history and tolerates missing sender names.
- Chat broadcast recipients are checked again after saving a message.
- Departure validation uses India time consistently in both applications.
- Custom date, time and vehicle controls accept keyboard input; the calendar's
  Today action respects its minimum date.
- Booking confirmation no longer claims an unpersisted vehicle-booking status;
  riders are asked to confirm it with the owner in chat.

## Verification

- Backend build and frontend build passed.
- Frontend lint and deployment configuration tests passed.
- Backend: 32 unit tests and nine HTTP/socket/email tests passed; one optional
  two-worker Redis test skipped because no disposable test Redis was configured.
- An isolated local React/DOM check passed three additional scenarios: changing
  search pages without stale metadata, showing request-load failures, and blocking
  duplicate join submissions. This used temporary tooling under the ignored
  `.deployment-check` directory; it added no application dependencies.
- Browser verification: clicking About Us from a scrolled local Safety page
  changed the route to `/about` and reset the scroll position to zero.
- The live home, About, Safety and sign-in pages rendered. Find/Offer access
  redirected a logged-out visitor to sign-in. The live backend health check
  returned JSON with status 200; unauthenticated session status returned 401;
  the login bridge redirected to Google. A mobile Safety-page check at 390px
  showed no horizontal page overflow.
- Both production dependency audits reported zero known vulnerabilities.

## Boundaries still requiring deployment validation

Pushing this branch does not establish which version the hosting providers deploy.
The live bundle still points directly to the existing backend; the local cookie
session design requires the documented same-origin proxy. Vercel's current
SPA-only rewrite returns HTML for backend paths and must not be treated as a
working API proxy for a new release. No hosting architecture was silently changed.

No authenticated Google account was used for production booking/profile/chat
tests. The local multi-user tests use isolated sessions and mocked database rows.
Redis integration, real transaction contention, a production workload and an
independent penetration test remain unverified. The existing database's ownership,
backup, reconciliation and baseline still require confirmation; this review did
not alter that database or assume any college server configuration.
